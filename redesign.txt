I think your assessment is on the right track. The biggest challenge isn't executing a workflow—it's providing a configurable workflow management experience that matches the client's requirements.

Here's how I would frame the architecture.

### Key observation

The client isn't simply asking for workflow execution. They want a **workflow management platform** where a Catalogue Admin can:

* create or modify workflows,
* configure steps, roles, timers and escalation,
* define triggers,
* monitor execution,
* troubleshoot running workflows.

A workflow engine (Camunda, Temporal, Flowable, n8n, etc.) solves only part of that problem. It executes workflows very well, but most of them expect workflows to be defined by developers rather than business users.

### What an external workflow engine gives us

Using an external engine provides:

* workflow state management
* task assignment
* timers
* retries
* escalations
* persistence
* APIs
* audit trail

What it **doesn't** provide (at least not in the way the client expects):

* a business-friendly UI for creating workflows
* CKAN-specific configuration
* trigger configuration
* integration with CKAN permissions
* monitoring embedded into the catalogue

So we'd still need to build a significant amount ourselves.

### I think there are two realistic architectures

#### Option 1 — Thin workflow engine + CKAN extension (my preferred approach)

Build a CKAN extension responsible for:

* Workflow Designer

  * configure steps
  * assign CKAN roles
  * configure timers
  * configure notifications
  * configure triggers

* Workflow Dashboard

  * active workflows
  * pending approvals
  * history
  * troubleshooting

* Workflow API

Then let an external engine execute the configured workflow.

The extension becomes the "brain" from the user's perspective, while the workflow engine becomes an implementation detail.

Advantages:

* users stay inside CKAN
* satisfies "Catalogue Admin configures workflows"
* reuse mature workflow engine
* easier to extend later

---

#### Option 2 — Entire workflow implemented inside CKAN

Everything lives inside a CKAN extension.

Pros

* completely integrated
* simpler deployment
* no extra infrastructure

Cons

* we reinvent workflow execution
* timers
* retries
* escalation
* task queue
* monitoring
* long-running process management

This becomes a large amount of custom development.

---

### I would avoid

Building everything in an external tool.

For example:

> "Workflow lives in Camunda and admins modify BPMN files."

or

> "Admins edit YAML."

For example, the UI could initially allow configuring:

That's enough to demonstrate that workflows are configurable without building a full drag-and-drop BPMN editor.

I was thinking a bit more about the architecture, and maybe we can split it into two separate responsibilities.

The workflow engine itself should only be responsible for execution. It would receive workflow definition, keep workflow state, assign tasks, handle timers, reminders, escalations and expose API to check workflow progress. This is what workflow engines are designed for, so I don't think it makes sense to implement this logic from scratch inside CKAN.

On the CKAN side we could develop a new extension which acts as workflow management layer. This extension would provide UI for Catalogue Admin to create new workflows or modify existing ones. For example, admin could define workflow steps, assign CKAN roles to each step, configure notifications, timeout values, escalation rules and also configure when workflow should start (new dataset, specific dataset type, metadata template etc.).

The extension would store workflow configuration in CKAN database and convert it into format accepted by the workflow engine. From user perspective everything still happens inside CKAN, while workflow engine is just executing what was configured.

When user creates or updates dataset, CKAN extension would evaluate configured triggers. If workflow should be started, dataset stays in Draft/Pending state and extension creates new workflow instance using workflow engine API. Every approval or rejection from workflow participants would be sent back to workflow engine, which decides what the next step is. Once workflow completes successfully, CKAN updates dataset state automatically to Published. If workflow is rejected, cancelled or timed out, extension can either keep dataset in Draft state or perform another configured action.

For monitoring we can also keep it inside CKAN. Admin would have dashboard showing all running workflows, current step, assigned user, overdue tasks and completed workflows. Most of this information can be requested from workflow engine API, so we don't have to duplicate execution logic inside CKAN.

I think this architecture gives us quite clean separation. CKAN stays responsible for configuration, permissions, UI and integration with datasets, while workflow engine is responsible only for orchestration. It also gives us possibility to replace workflow engine later if needed, because CKAN extension would be talking only through API.

For the demo we probably don't need to implement full workflow designer. Even simple UI where admin can configure workflow steps, roles, approvals and triggers should be enough to demonstrate that workflows are configurable by administrator and not hardcoded by developers.
